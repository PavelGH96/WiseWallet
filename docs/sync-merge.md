# Пооперационное слияние при синхронизации

**Реализовано в v4.45.** Документ описывает, как это устроено и почему
именно так; раздел «Что не так было» оставлен, потому что без него
непонятно, от чего защищает половина правил.

Код: функции `ww45*` в `index.html` (рядом с `ww44MergeSettings`),
синхронизация — `_syncNowInner`, проверки — `test/merge.js`.

Отличия от первоначального проекта, которые всплыли при реализации:

- **База — не снимок состояния, а карта отпечатков.** Полный снимок
  удваивал бы объём в localStorage без пользы: для слияния нужно знать
  только, менялась запись или нет, а это сравнение хэшей. Вышло ~25 КБ на
  тысячу записей вместо нескольких сотен.
- **Метки проставляются сравнением, а не вручную.** В проекте
  предполагалось вызывать `touch(rec)` в местах правки. На деле `save()`
  сравнивает состояние с отпечатком предыдущего сохранения — поэтому сотню
  мест, где правятся и удаляются записи, трогать не понадобилось, и ни одно
  из них не может «забыть» поставить метку.
- **Этапы 1–4 сделаны разом.** Разносить их во времени имело смысл при
  постепенной раскатке на устройства; здесь вся правка приезжает одной
  версией, а совместимость со старыми данными обеспечивают «устаревшие»
  метки (см. ниже).
- **Диалога конфликта больше нет** — вместе с ним ушли `wwLooksUntouched`,
  `wwPayloadWeight` и флаг намеренного сброса.

---

## 1. Что не так было

Состояние целиком лежит в одной строке `ww_user_state.data` (jsonb).
Синхронизация в `_syncNowInner()` сводится к выбору одной из двух версий:

```js
const remoteNewer = remote.data.updatedAt > S.updatedAt;
// → либо doPull() (взять серверную целиком), либо doPush() (отправить свою целиком)
```

Отсюда три следствия.

**Правки теряются молча.** Добавили расход с телефона, в это же время с
компьютера — заметку к другой операции. Выигрывает тот, у кого `updatedAt`
больше; вторая правка исчезает. Никакого признака потери нет: обе стороны
считают, что синхронизировались успешно.

**Диалог конфликта перекладывает выбор на человека.** Вопрос «оставить эту
или взять с сервера» требует помнить, что менялось на каждом устройстве за
день. Ответить на него правильно почти невозможно, а цена ошибки — день
работы.

**Запись не защищена от гонки.** `doPush()` делает безусловный upsert:

```js
const up = await fetch(`${sbUrl}/rest/v1/ww_user_state`, {
  method: "POST", headers: { ...H, Prefer: "resolution=merge-duplicates,..." },
  body: JSON.stringify([row]),
});
```

Между чтением и записью строка могла измениться. Проверки на это нет, и
чужая запись затирается без следа.

Вокруг этого уже наросла защита: `wwLooksUntouched()`, `wwPayloadWeight()`,
`WW_RESET_FLAG`, `ww50DataSignature()`. Это заплатки на один частный
случай — «пустая установка не должна затереть облако». Они нужны ровно
потому, что единица синхронизации выбрана неправильно: не запись, а всё
состояние сразу. После перехода на слияние большая часть этой обвязки
убирается.

---

## 2. Что получилось

1. Параллельные правки разных записей сливаются без вопросов.
2. Правки одной и той же записи разрешаются детерминированно: оба
   устройства приходят к одному результату независимо от порядка обмена.
3. Удаление не отменяется другим устройством, которое про него не знало.
4. Пустое или старое устройство не способно стереть чужие данные.
5. Диалога конфликта нет вовсе: не осталось случая, где выбор нельзя
   сделать машинально. Единственное исключение — хранилище паролей
   (раздел 3.5), но и там вопрос задаётся про один зашифрованный блоб,
   а не про всё состояние разом.
6. Формат меняется совместимо: старые данные продолжают открываться,
   метки для них выводятся из самих записей.

---

## 3. Решение: трёхсторонее слияние с метками на записях

Две части: метки времени на каждой записи и база — снимок того состояния,
на котором устройства в прошлый раз сошлись.

### 3.1. Метка на записи

Каждая запись в коллекциях (`transactions`, `credits`, `recurring`,
`budgets`, `goals`, `accounts`, `categories`, `tasks`, `links`) получает
служебное поле:

```js
t.u = { t: 1763467200000, d: "k3n8" }   // когда и на каком устройстве изменено
```

`d` — идентификатор устройства: четыре случайных символа, живёт в
localStorage (`ww_device_id`), в облако не попадает ничем, кроме этой
метки. Нужен только для устойчивого разрешения ничьей: при равных `t`
побеждает лексикографически больший `d`. Без этого два устройства могут
выбрать разные версии и начать перекидывать их друг другу.

Поле называется коротко (`u`, а не `updatedAt`) намеренно: оно добавляется
к каждой операции, а состояние целиком ходит по сети при каждой
синхронизации. На тысяче операций разница между `u` и `updatedAt` — около
15 КБ на запрос.

Проставляется в одном месте — в `save()`:

```js
function touch(rec) { rec.u = { t: Date.now(), d: wwDeviceId() }; return rec; }
```

Все места, где меняется запись, уже проходят через `save()`, так что
правка точечная. Важно именно помечать изменённую запись, а не
проставлять метку всем подряд при сохранении: иначе каждая запись будет
выглядеть изменённой и слияние выродится обратно в «кто последний».

### 3.2. Удаление: надгробия

Удаление перестаёт быть `splice()` из массива. Вместо этого:

```js
S.graves = {
  transactions: { "tx_8812": 1763467200000, ... },
  credits: { ... },
};
```

Запись с `id` в `graves` считается удалённой и не показывается. Правило
разрешения: удаление побеждает правку, если `graves[id] >= rec.u.t`.
Правка новее надгробия воскрешает запись — это нужно, когда человек
осознанно вернул операцию после удаления на другом устройстве.

Надгробия чистятся по возрасту: старше 90 дней — удаляются. Срок
выбирается из простого соображения: устройство, не выходившее на связь
дольше этого срока, может воскресить удалённые записи. 90 дней с запасом
покрывают отпуск и забытый планшет; хранение обходится в ~40 байт на
удалённую запись.

При чистке надгробий состояние становится «неполным» для очень старого
устройства. Защита — пункт 3.5.

### 3.3. База для трёхстороннего слияния

Одних меток мало. Нужно отличать «запись не менялась у меня» от «запись у
меня была удалена» — иначе невозможно понять, кто кого должен победить.
Для этого храним снимок последнего согласованного состояния:

```js
localStorage["ww_sync_base_v1"] = JSON.stringify(stateAtLastSync);
```

Снимок пишется после каждой успешной синхронизации — ровно то состояние,
которое в этот момент лежит на сервере. На нём строится слияние:

| база | локально | удалённо | результат |
|------|----------|----------|-----------|
| есть | не менялась | изменена | версия с сервера |
| есть | изменена | не менялась | локальная |
| есть | изменена | изменена | по `u.t`, при равенстве — по `u.d` |
| есть | удалена | не менялась | удалить |
| есть | удалена | изменена | надгробие vs `u.t` (п. 3.2) |
| нет | есть | нет | добавить (новая локальная) |
| нет | нет | есть | добавить (новая удалённая) |

Хранится база не снимком, а картой отпечатков: `{ lists: { transactions:
{ id: "1f3a9c" } }, dicts: {…}, settings: {…} }`. Полный снимок удваивал
бы объём в localStorage, а для слияния нужно ровно одно — ответ на вопрос
«менялась запись или нет», то есть сравнение отпечатков. Выходит около
25 КБ на тысячу записей; пишется база после каждой успешной
синхронизации (`ww45BaseSave`), читается перед слиянием
(`ww45BaseLoad`).

### 3.4. Коллекции, которые не массивы

Часть состояния — не списки записей, а словари с составными ключами:

| поле | ключ | что это |
|------|------|---------|
| `S.posted` | `recurringId:YYYY-MM` | сколько проведено по регулярному платежу |
| `S.skipped` | `recurringId:YYYY-MM` | платёж пропущен в этом месяце |
| `S.ww30Cr` | `creditId:YYYY-MM` | отметки оплаты по кредиту |
| `S.ww34Order` | `kind` | порядок строк в панели «К оплате» |
| `S.recurIncomeAmt` | `recurringId:YYYY-MM` | сумма дохода, заданная на месяц |

У них нет места под `u`. Заводим параллельный словарь меток:

```js
S.meta = { "posted:r1:2026-11": { t: 1763467200000, d: "k3n8" }, ... };
```

Слияние — по тем же правилам, ключ к ключу. Это честнее, чем кажется:
такие ключи по смыслу независимы (оплата коммуналки в ноябре ничего не
знает про оплату интернета в декабре), и параллельные правки разных
месяцев сливаются без конфликта.

Отдельный случай — `S.ww30Cr[key].payments`: массив внутри значения.
Сливается объединением по `txId`, `paid` пересчитывается суммой. Это
единственное место, где нужно не LWW, а именно объединение: иначе
частичная оплата с одного устройства затрёт частичную с другого, хотя обе
реальны и обе уже записаны отдельными операциями.

### 3.4а. Сходимость: два правила, без которых всё это не работает

Оба нашлись не на уровне функции слияния, а когда два настоящих
устройства заработали против одного сервера. Симптом в обоих случаях
одинаковый и обманчиво безобидный: данные у всех совпадают, но строка в
базе переписывается бесконечно — каждое устройство видит в чужой версии
изменение и честно отправляет своё.

**Порядок записей.** Счета и категории переставляются перетаскиванием,
то есть порядок — такие же данные, как суммы. Если при слиянии ставить
первым «свой» порядок, второе устройство немедленно вернёт свой. Поэтому
перестановка получает отдельную метку `meta["order:<коллекция>"]`, и
порядок берётся у того, кто переставлял позже. Когда не переставлял
никто, метки совпадают — тогда выбор делается по самой
последовательности (лексикографически меньшая), а не «локальный всегда
прав»: только так обе стороны приходят к одному ответу.

Перестановкой считается изменение взаимного порядка записей, которые
были и остались. Добавление в конец и удаление из середины
последовательность меняют, но перестановкой не являются — иначе метка
порядка обновлялась бы при каждой новой операции, и весь порядок списка
диктовало бы устройство, на котором последним что-то завели.

**Одинаковые записи с разными метками.** `ww2Migrate` добавляет
служебные категории переводов при первом запуске — на каждом устройстве
свою, с одинаковым содержимым и разным `u`. Вернуть при слиянии «свою»
нельзя по той же причине. Берётся более ранняя метка: запись одна и та
же, и её настоящее время появления — первое.

Общее правило, которое из этого следует: **при равном содержимом
результат должен быть равен побайтово, вместе со служебными полями.**
Проверка «данные совпали» этого не ловит, поэтому в тестах сходимость
сверяется по `ww45StateHash`, а в сквозном тесте есть отдельный пункт
«холостая синхронизация не пишет в базу».

### 3.5. Что НЕ сливается

**Хранилище паролей** (`S.pwVault`) — один зашифрованный блоб: внутрь без
мастер-пароля не заглянуть. Выбирается версия целиком по метке
`meta["pwVault"]`.

**Журнал изменений** (`S.audit`) — объединение по `id`, сортировка по
`ts`, обрезка до `WW331_MAX_LOG`. Конфликтов не бывает: записи только
добавляются.

**Настройки** — пер-ключевое слияние с метками, как в 3.4, поверх
разделения на общие и привязанные к устройству из v4.44
(`ww44MergeSettings`, `WW44_LOCAL_SETTINGS`): адрес проекта, ключ и
отметки синхронизации всегда остаются локальными.

**Слишком старое устройство.** Если базы нет, остаются метки и
надгробия: удаление с надгробием по-прежнему побеждает более раннюю
правку, а записи, которых нет на другой стороне, просто добавляются.
Теряется только защита от отстающих часов (раздел 3.3) — её даёт именно
база. Проверяется сценарием 10 в `test/merge.js`.

## 4. Защита записи от гонки

Слияние бессмысленно, если результат затирается чужой записью. Нужен
compare-and-swap, и для него не требуется менять схему: PostgREST умеет
фильтровать строки при обновлении.

```js
// читаем
const res  = await fetch(`${url}/rest/v1/ww_user_state?user_id=eq.${uid}&select=data,updated_at`, { headers: H });
const base = (await res.json())[0];

// сливаем
const merged = wwMerge(localState, base.data, syncBase);

// пишем, только если строка с тех пор не менялась
const up = await fetch(
  `${url}/rest/v1/ww_user_state?user_id=eq.${uid}&updated_at=eq.${encodeURIComponent(base.updated_at)}`,
  { method: "PATCH",
    headers: { ...H, Prefer: "return=representation" },
    body: JSON.stringify({ data: merged, updated_at: new Date().toISOString() }) });

const rows = await up.json();
if (!rows.length) {
  // кто-то записал между нашим чтением и записью — перечитать и слить заново
  return retry();                  // не более 3 попыток, потом отложить до следующей синхронизации
}
```

Пустой ответ при `return=representation` означает «ни одна строка не
подошла под фильтр», то есть `updated_at` изменился. Это и есть признак
гонки — без триггеров, функций и новых таблиц.

Первая запись (строки ещё нет) остаётся upsert'ом, но с
`Prefer: resolution=ignore-duplicates`: если строку успели создать
параллельно, вставка не затрёт её, и следующий проход сольёт нормально.

## 5. Что где лежит

| что | где |
|-----|-----|
| `wwDeviceId`, `ww45Hash`, `ww45Stamp`, `ww45Merge`, `ww45Apply`, база | `index.html`, блок «v4.45: пооперационное слияние» |
| простановка меток | вызов `ww45Stamp(S)` в `save()` |
| чтение, слияние, запись с проверкой | `_syncNowInner` |
| живое слияние | обработчик `postgres_changes` в `ww36RealtimeInit` |
| сброс данных с надгробиями | `resetAll` |
| пересборка опорного снимка журнала | `ww331Rebase` |
| проверки | `test/merge.js` (28 сценариев) и раздел «Синхронизация» в `test/run-all.js` |

Совместимость со старыми данными. У записей, заведённых до v4.45, метки
нет. При первом сохранении она проставляется не текущим временем, а
временем из самой записи (`updatedAt` → `createdAt` → `updatedAt`
состояния) и с пустым идентификатором устройства. Благодаря этому одна и
та же нетронутая запись получает на всех устройствах одинаковую метку:
отпечатки совпадают, и сливать нечего. Записи стартового набора помечены
нулём — свежая установка не может победить облако своими «Бытовыми
расходами».

## 6. Как проверять

`ww45Merge` — чистая функция (не трогает `S`, не ходит в DOM и не смотрит
на часы), но живёт внутри `index.html`, поэтому проверки выполняются в
настоящей странице: так тестируется ровно тот код, который работает у
пользователя, а не его копия в отдельном модуле.

Два устройства разыгрываются в одной вкладке — `ww45Stamp` принимает
`{ now, dev, prev }`, так что у каждого свои часы, свой идентификатор и
свой отпечаток предыдущего сохранения.

Набор сценариев (`test/merge.js`):

1. Правки разных записей с двух устройств — обе на месте.
2. Правка одной записи с двух устройств — выигрывает та, что по `u.t`
   новее; при равных `t` обе стороны выбирают одно и то же по `u.d`.
3. Удаление на A, правка той же записи на B раньше удаления — запись
   удалена.
4. Удаление на A, правка на B позже удаления — запись жива.
5. Добавление на A при удалении другой записи на B — оба изменения
   применились.
6. Частичные оплаты по одному кредиту с двух устройств — суммируются,
   `paid` сходится с суммой `payments`.
7. Слияние идемпотентно: `merge(merge(a,b,base), b, base) === merge(a,b,base)`.
8. Слияние симметрично: результат не зависит от того, кто синхронизируется
   первым.
9. Пустое устройство против непустого облака — данные не теряются.
10. Устройство с просроченной базой — полный pull, локальные новые
    записи добавлены, удалённые не воскресли.

Пункты 7 и 8 проверяются не вручную собранными случаями, а генератором
случайных последовательностей правок: 200 прогонов по 1–3 операции на
каждое устройство (правка, удаление, добавление, запись в словарь), и
после каждого — сравнение `merge(a,b)` с `merge(b,a)`, повторного слияния
с однократным и состояний обоих устройств после обмена.

Сами проверки тоже проверены: если убрать из `ww45Merge` учёт надгробий,
сверку с базой, объединение частичных оплат или выбор по метке — падают
ровно те сценарии, которые за это отвечают. Набор, который не краснеет
на сломанном коде, не стоит ничего.

Проверки идут тремя уровнями, и каждый ловит своё:

| уровень | файл | что ловит |
|---------|------|-----------|
| функция слияния | `test/merge.js` | правила выбора версии, надгробия, словари, настройки, 200 случайных прогонов |

## 7. Что осталось за рамками

**Хранилище паролей не сливается по записям** — это один зашифрованный
блоб, внутрь без мастер-пароля не заглянуть. Выбирается версия целиком по
метке. Чтобы сливать и его, пришлось бы шифровать каждую запись отдельно;
это осмысленная задача, но отдельная.

**Поля внутри одной записи не сливаются.** Если один исправил сумму, а
второй — заметку той же операции, победит правка целиком. Пофайловое
слияние потребовало бы меток на каждое поле: рост объёма заметный, выигрыш
для личного учёта — редкий случай.

**Отдельные таблицы на запись** (`ww_transactions`, `ww_credits`, …)
вместо одной строки с JSON дали бы слияние на стороне базы и обмен только
изменившимся. Это другая архитектура: схема, миграция, RLS на каждую
таблицу, пагинация, офлайн-очередь. Для одного пользователя с парой
устройств выигрыш не окупает работу — к этому стоит возвращаться, если
появятся общие бюджеты на несколько человек.
